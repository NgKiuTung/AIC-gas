# 生产模型重训与重载一致性实验报告

## 1. 实验目的

本实验整改审计项 P0-02。此前仓库报告的 5.4671% 来自 d5/d4/d6 OOF 组合，但磁盘可加载模型仍是 5.5528% 的旧单模型，构成 Research/Serving Skew。本阶段严格按照 Phase 1 冻结的 `configs/model_spec.yaml`，仅用官方训练期派生特征重训实际生产组件，并验证序列化、重载和 CPU 推理一致性。

本阶段未读取、枚举或训练使用评分测试集，也未根据官方评分反馈修改参数。

## 2. 冻结输入

- 训练行：10,832；
- 特征数：801；
- 特征组：base、clean_view、difference、lag、mechanism_ratio、rolling、smooth、transition；
- 目标：`generator_1` 相对修正量 + `generator_all` 绝对修正量，共 16 个输出；
- 最终非零组件：d5、d6；
- d4 最终权重为 0，不进入生产 bundle；
- 特征缓存 SHA-256：`313e485a2b6cb763af83cff9344a7d13f581ee17840c26a11a18100667a84f7f`；
- 特征目录 SHA-256：`724b501c476e9c6526b74da329e7add4279a85d316d5b57e78be14d666ad973d`。

## 4. 序列化与 CPU 一致性

训练时先在 256 行尾部样本比较保存前、重载后和 CPU 推理，两个组件最大绝对差均为 0。随后独立验证器只加载模型、不执行 fit，并对全部 10,832 行进行检查：

- 特征名、数量和顺序与冻结 schema 完全一致；
- 输入缓存、目录、schema 和模型文件哈希全部一致；
- d5/d6 输出均为 `(10832, 16)` 且无 NaN/Inf；
- 全量 GPU/CPU 最大绝对差均为 0；
- 22/22 项 bundle 检查通过；
- 仅“已构造特征 → 两模型 CPU 预测 → 冻结集成”耗时 0.269 秒。

该 0.269 秒不是官方完整端到端耗时，因为尚未包含四张原始表加载、预处理和因果特征构造。完整链必须在 Phase 3–4 再做 30 分钟约束验证。

## 5. 物理层级问题与整改

第一次全量检查发现，未做物理投影时 86,656 个“行 × 步长”预测中有 4 个出现 `generator_all < generator_1`，比例约 0.00462%，最大差 2.2659。该问题在 256 行尾部 smoke test 中未出现，因此证明只做尾部抽样不足。

生产后处理现冻结为：

```text
generator_all = max(generator_all, generator_1)
```

对 Phase 1 的 7,360 个嵌套外层目标组合进行复核时，层级违反为 0，因此加入投影不会改变已报告的 4.7149% MAPE。投影后全量生产 bundle 层级检查通过。

## 6. 验收结论与剩余风险

Phase 2 验收通过：README、ModelSpec、实际磁盘模型及生产 manifest 已指向同一套 d5/d6 组件，Research/Serving Skew 已关闭。

当前仍不能生成正式提交：

1. 正式运行环境仍是 Python 3.13.7，不符合官方建议的 3.8–3.10，需在 Phase 5 使用 Python 3.10 复验；
2. 当前验证入口从已经构造好的 801 维特征开始，尚未实现官方四张原始表到因果特征的链路；
3. 评分测试集仍处于禁止访问状态；只有 Phase 3 的独立 submission inference policy 才能只读加载，且不得 fit、调参或计算评分标签指标；
4. 模型二进制已进入本地私有版本 `v0.4.0-model`，归档校验 4/4 通过；该目录不得上传 GitHub Release。

下一阶段为 Phase 3：构建训练策略与评分只读策略分离的原始表因果推理入口，并先用合成原始表完成端到端测试。
